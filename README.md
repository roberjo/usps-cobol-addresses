# AMS Edit Book Update — a mainframe COBOL batch job, recreated on a laptop

[![ci](../../actions/workflows/ci.yml/badge.svg)](../../actions/workflows/ci.yml)

A hobby recreation of a mainframe-style COBOL/DB2 batch system, modeled on the
USPS Address Management System (AMS) *Edit Book Update* process. Carriers mark
up printed route listings ("edit books") with new construction, vacancies, and
unit splits. This job validates those edits, applies them to the address
master, re-sequences each route's delivery order, and prints the run report
and updated edit books.

It runs end to end on a Mac (or any Docker host) with GnuCOBOL, the GixSQL
embedded-SQL precompiler, and PostgreSQL standing in for DB2 for z/OS. It is
tested the way a mainframe shop would want it tested: paragraph-level unit
tests, byte-for-byte golden files, and an abend/restart drill, all in CI.

> **Framing.** This is a personal learning and portfolio project, inspired by a
> public job posting for COBOL support on AMS. It is not affiliated with or
> derived from USPS systems or code. All addresses are generated by Faker in
> the unassigned ZIP range `000xx`.

## Quick start

Needs Docker with Compose (Docker Desktop, or Colima + `docker-compose`).

```bash
make image    # build the toolchain image: GnuCOBOL 3.2, GixSQL, cobol-check (~10 min once)
make ci       # lint, compile, unit tests, full job run, golden-file regression
make run      # just run the job; outputs land in data/out/
```

`make shell` opens a shell inside the toolchain, where the same targets run
directly (`make reset-db`, `make run`, `jobs/ebupd01.sh --restart`, ...).

## The job: `EBUPD01`

```text
 data/in/ebtrans.dat                ctl/ebupd01.sysin  (control cards → every step)
 80-byte EBTRANS records
        │
        ▼
 STEP010 EBVALID ──(+EBVRULES)────► EBREJ   validation rejects + reason ─────────┐
        │   singleton SELECT on ams_route                                         │
        ▼                                                                         │
 STEP020 EBSORT   ZIP5 ▲  route ▲  seq ▼  action ▼  (D before C before A)         │
        │                                                                         │
        ▼                                                                         │
 STEP030 EBUPDT ◄──► ams_address, eb_checkpoint (Postgres "DB2") ─► EBAUDIT ──────┤
        │   commit every N, checkpoint, restart                   ─► EBUREJ ──────┤
        ▼                                                                         ▼
 STEP040 EBRPT  ─────────────────► EBRPT  132-col report (ASA)   +   EBBOOK extract
```

| Step | Program | What it does | Return codes |
| --- | --- | --- | --- |
| 000 | (script) | Deletes last run's datasets, IEFBR14 style. Refuses to run if an unfinished checkpoint exists. | 12 |
| 010 | `EBVALID` + `EBVRULES` | Field edits (action, ZIP, ZIP+4, required fields, dates, packed sequence, LOW/HIGH-VALUES) and a route lookup. | 0 / 4 / 8 if rejects > `REJMAX`% / 12 |
| 020 | `EBSORT` | COBOL `SORT` verb, same keys as the DFSORT card in the JCL. | 0 / 12 |
| 030 | `EBUPDT` | Soft deletes, changes, and inserts with resequencing. Commit/checkpoint every `COMMIT=` records; `RESTART=Y` resumes. | 0 / 4 / 12 / 16 (drill) |
| 040 | `EBRPT` | Reject listing, reason summary, per-route totals, and a cursor-driven edit book extract for every changed route. | 0 / 12 |

Steps follow JCL `COND=(8,LE)` rules: an RC 8 from validation skips the sort and
update, but the report still runs so the rejects get printed. The reference JCL
is [`jcl/EBUPD01.jcl`](jcl/EBUPD01.jcl), and the runnable equivalent is
[`jobs/ebupd01.sh`](jobs/ebupd01.sh). Each `//DD` becomes a `DD_<NAME>`
environment variable, which GnuCOBOL uses to resolve `ASSIGN TO <NAME>`.

## What a run looks like

```text
$ make run
EBUPD01 STEP010  EBVALID ENDED RC=0004      210 read, 191 passed, 19 rejected (9.05%)
EBUPD01 STEP020  EBSORT ENDED RC=0000
EBUPD01 STEP030  EBUPDT ENDED RC=0004      187 applied, 4 rejected, 8,045 rows resequenced
EBUPD01 STEP040  EBRPT ENDED RC=0000
EBUPD01 EBUPD01  ENDED MAXCC=0004
```

The delivery sequence is packed decimal, so you can read it in hex, the way
you would in ISPF browse with `HEX ON`:

```text
$ xxd -l 20 data/in/ebtrans.dat
00000000: 4130 3030 3131 4330 3032 0000 119c 3133  A00011C002....13
                                    └──┬────┘
                          PIC S9(7) COMP-3 = +119
```

`make ebcdic-demo` converts the file to EBCDIC and back. It shows that a blind
whole-record conversion turns `x'0000119C'` into `x'000011E6'`, which is
invalid packed data and would cause an S0C7 on the host.

## Testing

| Layer | Tool | What it covers |
| --- | --- | --- |
| Lint | `make lint` | Fixed-format COBOL must stay in columns 8–72. The compiler silently ignores 73+. |
| Unit | [cobol-check](https://github.com/openmainframeproject/cobol-check) | 20 test cases against the `EBVRULES` paragraphs ([`tests/unit`](tests/unit/EBVRULES/EBVRULES.cut)). |
| Golden files | pytest | Every job output, the job log, and the database rows for the changed routes must match [`tests/golden/`](tests/golden) byte for byte. |
| Oracle | pytest + [`tests/model.py`](tests/model.py) | An independent Python model of the business rules predicts the final database state and the reject counts. |
| Modes | pytest | `MODE=VALIDATE` rolls back; `REJMAX` exceeded stops before the update; a bad control card gives RC 12. |
| Restart drill | pytest | Abend EBUPDT after record 120 (`COMMIT=50`), check the job refuses a plain resubmit, restart, and match the clean run. |

When an output is supposed to change, run `make golden` and commit the new
golden files with a message that says why.

## Mainframe → local mapping

| Mainframe | Here | How close |
| --- | --- | --- |
| Enterprise COBOL | GnuCOBOL 3.2, `-std=ibm` (fixed format, WORKING-STORAGE starts as binary zeros) | High |
| DB2 for z/OS + precompiler, `EXEC SQL` | PostgreSQL 16 + GixSQL 1.0.20b | Medium; see [`sql/db2-notes.md`](sql/db2-notes.md) |
| JCL, DD statements, COND codes | [`jobs/ebupd01.sh`](jobs/ebupd01.sh), `DD_<NAME>` env vars | High conceptually |
| DFSORT | COBOL `SORT` verb in `EBSORT` | Medium |
| EBCDIC datasets, COMP-3 | `tools/ebcdic.py` (cp037, field-aware) | High |
| Checkpoint/restart | `eb_checkpoint` row committed with each unit of work | High |
| `-debug` / `-fec=all` runtime checks | Data exceptions (S0C7-style), subscript checks | High |
| ChangeMan packages, ServiceNow | Git branches + [`tickets/`](tickets) templates | Concept only |

## Repository layout

```text
src/            COBOL programs: EBVALID, EBVRULES, EBSORT, EBUPDT, EBRPT
copybooks/      Record layouts, control-card and DB paragraphs, reason codes
jcl/            Reference z/OS JCL (not executed)
jobs/           Runnable shell equivalent of the JCL
ctl/            SYSIN control cards
db/             schema.sql, seed.sql (generated)
data/in/        ebtrans.dat (generated; committed so golden files stay stable)
tools/          gen_data.py, ebcdic.py, dump_db.sh, ebcdic_demo.sh
tests/          pytest regression, model.py oracle, golden/, unit/ (cobol-check)
docs/           ICD, operations runbook, gotchas write-up
sql/            DB2 vs. PostgreSQL/GixSQL notes
tickets/        INC/CHG templates for the maintenance workflow
docker/         Toolchain image
```

## Limitations

Not reproduced: z/OS operations (SDSF, abend dumps, GDG and space management),
DB2 BIND/plans/EXPLAIN/locking, ChangeMan screens and approvals, and decades of
undocumented business rules in the real system. See `project-details.md` for
the full list and next steps.
